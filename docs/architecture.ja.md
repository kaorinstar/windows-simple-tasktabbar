## なぜ src と tests を分けるのか

.NET の一般的な構成に合わせています。ソースとテストが同じ階層に並ぶと、
プロジェクトが増えたときに見分けがつかなくなります。

## なぜ Core を分けるのか

`WindowsSimpleTaskTabBar.Core` には、画面やWindows APIに依存しない処理だけを置きます。
これにより次の2点が実現します。

1. **どのOS上でもテストできます。** Windows API に依存する処理はWindows上でしか動かないため、
   混ざっているとテストの実行環境が限られます。
2. **テストの対象が明確になります。** 計算やルールの判定は Core に置き、画面の描画とAPI呼び出しは
   アプリ本体に置く、という切り分けです。

対象フレームワークは `netstandard2.0` です。.NET 8 と .NET Framework 4.8 の両方から使えます。

なお、アプリ本体は Core を **DLLとして参照せず、ソースを直接取り込んでいます**。
DLL参照にすると配布ファイルが2つになり、「実行ファイル1つで配れる」という利点が失われるためです。
テストプロジェクトは Core をライブラリとして参照します。

## 2つのフレームワークを同時に作る仕組み

`src/WindowsSimpleTaskTabBar/WindowsSimpleTaskTabBar.csproj` の `TargetFrameworks` に2つ指定しています。

```xml
<TargetFrameworks>net8.0-windows;net48</TargetFrameworks>
```

1回のビルドで、次の2つが同時に作られます。ソースコードは共通です。

- `net48`：Windows に標準で入っている .NET Framework 4.8 向け。配布先の準備が不要です。
  **配布するのはこちらだけです。**
- `net8.0-windows`：.NET 8 向け。毎回ビルドとテストを行いますが配布はしません。同じソースを
  別のコンパイラで検査する目的と、将来 .NET Framework が使えなくなった場合の備えです。

.NET 8 を同梱した版も一時期配布していましたが、取りやめました。約69MBかつ x64専用で、
利点があるのはサポートが終了したWindowsに限られ、そこには .NET Framework 4.8 を後から
導入できるためです。

フレームワークごとの差は、`Program.cs` の `#if NETFRAMEWORK` で切り分けています。

## 層の関係

```
Program.cs
   ↓
UI/MainForm.cs  ──→  Core/Layout/（計算）
   │             ──→  Core/Grouping/（どのタブがどのグループか）
   │             ──→  Core/Focus/（どのタブに前面の印を付けるか）
   │             ──→  Core/Localization/（画面に出す文言）
   ↓
Services/WindowService.cs（ウィンドウ操作）
   ↓
Interop/NativeMethods.cs（Windows API）
```

上の層から下の層だけを呼びます。逆向きの呼び出しはしません。
`NativeMethods` の呼び出しは `Interop` に閉じ込め、他の場所には書かない方針です。

## 前面のタブの示し方

前面にあるウィンドウのタブには輪郭線を描きます。それ以外は他のタブとまったく同じです。大きさも
位置も、アイコンと文字の置き方も変えません。

色だけでは足りませんでした。アクティブなタブの塗りと通常のタブの比は、明るい配色で1.27対1、
暗い配色で1.63対1です。WCAG は画面部品の区別に3対1を求めます。塗りだけでこれを満たすには、
明るいバーの中で中間的な灰色のタブが必要になり、1つを目立たせるために他のすべてを暗くする
ことになります。そこで `BarPalette.TabActiveOutline` が区別を担い、`BarPaletteTests` が
塗りと背景の両方に対して3対1を保っていることを確かめます。

アクティブなタブを高く描く案は先に試し、取りやめました。グループの色はタブの上端に沿って引かれ、
`DrawGroupBand` はそれをタブ本来の上端に置くことで、行全体で1本につながるようにしています。
1つのタブだけを高くすると、その色帯が隣のタブと共有する上端から下がり、角の丸みで整えていた
両端も四角くなります。グループが1つのまとまりとして読めるべき場所で、色帯がずれてしまいます。
上端は高さと色帯の両方の持ち物にはできません。

輪郭線は色帯より先に描きます。これによりグループのタブは色帯の太さを保ち、輪郭線は左右で
区別を担います。下端は輪郭線1本分だけバーの外へ出します。輪郭線は閉じた形をなぞるため、
最下行に下辺が残るとタブの下に線が引かれてしまいます。バーの端に立つタブの足元は開いている
べきです。

### どのタブに印を付けるか

前面のウィンドウをそのまま使うわけではありません。バーはクリックされると自分自身を前面に
します。これはウィンドウの切り替えを確実にするための設計です。そのため、バーに触れた時点で
前面は利用者が使っていたウィンドウから移ります。クリックの場合は離した時点で `ClickTab` が
戻します。ドラッグの場合は戻しません。前面にすべきウィンドウがないまま終わるため、バーが
前面のまま残り、次にどこかを選ぶまでどのタブにも印が付きません。塗りの色だけのころは
気づきにくい動作でしたが、輪郭線では目立ちます。

そこで `WindowToMark` は `Core/Focus/ActiveMark.cs` に判断を任せます。このアプリ自身の
ウィンドウは印を受け取らず、直前に印を持っていたウィンドウがそのまま保ちます。Windows の
タスクバーが、タスクバー操作中も直前のウィンドウの強調表示を保つのと同じ考え方です。バーが
一覧に載せていないウィンドウも印を持てないため、閉じたあとに再利用された同じ番号のウィンドウが
印を引き継ぐことはありません。

`ActiveMark` にはウィンドウの番号ではなく3つの真偽値を渡します。規則自体はどの環境でも
テストでき、どのウィンドウが何かを Windows に尋ねる部分は画面側に残ります。`IsOwnWindow` は
番号ではなくプロセス番号で比べます。このアプリが画面に出すウィンドウはバーだけではなく、
設定画面やメニューがクリック後の前面になることがあるためです。

タイミングに頼っていた箇所も併せて確実になります。`ClickTab` はすでに前面にあるタブを
最小化しますが、その判定に `tab.Active` を読みます。これまでは押してから離すまでの間に
250ミリ秒の更新が走るかどうかに左右されていました。バーが前面の間は印が動かなくなるため、
どちらでも同じ結果になります。

幅を広げる案も検討して見送りました（#9）。`TabStrip.Measure` は行全体に1つの幅を返し、4か所が
それを読みます。幅が2種類になると4か所すべての作り替えが必要です。またアクティブなタブは
ウィンドウを切り替えるたびに移るため、幅も変わり、その右にあるタブがすべて動きます。目当ての
ウィンドウへ即座に到達するためのバーとしては逆効果です。

## 画面の文言の持ち方

画面に出す文字は、表示する場所には書きません。1つずつ `Core/Localization/StringId.cs` で
名前を付け、`Core/Localization/UiStrings.cs` の言語ごとの表に文言を並べます。`UiText` は、
その表から1つの言語を読み出す窓口です。英語が原文で、他の言語はその翻訳です。

**`.resx` とサテライトアセンブリではなく、ただの表にしています。** サテライトアセンブリは
言語ごとにフォルダーとDLLが増えます。このアプリは実行ファイル1つで配布するため、表は
他の Core の処理と同じように実行ファイルへ組み込みます。どのOSでもテストできる利点も
あります。単体テストで2点を保証しています。すべての表がすべての名前に答えること、
どの表にも余分な名前がないことです。

**言語を1つ増やす作業は、表を1つと行を1つ追加するだけです。** 表は `UiStrings` に、行は
`Languages.All` に追加します。設定画面はその一覧をそのまま表示し、各言語をその言語自身の
名前で並べます。他の場所を直す必要はありません。Windows の表示言語がどの言語に当たるかは
`Languages.Canonical` が判定します。中国語とポルトガル語は2文字の言語コードだけでは
決まらないため個別に扱い、それ以外は2文字で判定します。

**内容を確認できているのは英語と日本語だけです。** テストはすべての表が同じ名前をそろえて
いることを保証しますが、訳の正しさは保証しません。訳の誤りは、その言語を読む人からの
指摘を受けて直します。

**書体は言語に合わせて選びます。** 中国語・日本語・韓国語は文字コードを共有しているため、
1つの書体ではまかなえません。日本語用の書体で中国語を表示すると、日本語の字形で出ます。
中国語の利用者には、文字が出ないのではなく、誤った字形に見えます。各言語の書体は
`Languages.All` に書き、`UI/UiFonts.cs` が、その書体が入っていない環境では Windows が
ダイアログに使う書体へ切り替えます。

**言語の変更は、他の設定と同じくその場で反映します。** バーはメニューと書体を作り直し、
設定画面は最初に画面を組み立てたのと同じ処理で自分を組み立て直します。どの部品にどの文言が
入るかという一覧を二重に持たないためです。2か所だけは、変更の処理が終わるのを待ちます。
設定画面の作り直しは、変更のきっかけになった選択欄自身を破棄するため `BeginInvoke` で
遅らせます。バーが差し替えた古いメニューは、終了時まで保持します。設定画面を開いたメニューは、
Windows Forms 側がまだ保持しているためです。

## アプリ単位で行をまとめる仕組み

`Core/Grouping/TabGrouping.cs` は、画面にもWindows APIにも依存しない2つの判断を担います。
どのタブがどのグループに属するかと、行をどの順で描くかです。バーはタブごとのグループ名を渡し、
並び順を受け取ります。この規則は単体テストで確かめられます。

`Arrange` は、すでに並べ替えたあとの行を渡されたら、そのまま返さなければなりません。
`RefreshTabs` は毎秒4回動くため、2回目で動いてしまうものは3回目でも動き、行が落ち着かなく
なるからです。グループは最初のウィンドウの位置に置き、グループ内の順序は元のまま保つことで、
これが成り立ちます。

並べ替えるのは `_tabs` ではなく `_order` です。`_order` は次の更新をまたいで残る表示順であり、
ドラッグは同じ添字で両方のリストを動かします。片方だけを並べ替えると、2つの内容が食い違います。
そのため、グループ化を無効に戻しても、タブはグループ化後の位置に残ります。開いた順はどこにも
記録していないためです。

**ドラッグは、グループの中ではタブ1枚を、グループの外へ出るとグループごと動かします。**
どちらになるかは `TabGrouping.PlanDrag` が決め、`TabStrip.MoveRange` が適用します。適用先は
内容を一致させる必要がある3つ、`_order`、`_tabs`、そして次のドラッグ判定が読むグループ名の
並びです。

タブ1枚だけをグループの外へ出すことはできません。グループ分けは次の更新で計算し直すため、
外へ出たことを記録する場所がなく、250ミリ秒以内に元へ戻るからです。利用者がたった今行った
操作を勝手に元へ戻す動きは、そもそも動かせない動きより分かりにくくなります。

グループごとであれば、この問題は起きません。理由は `Arrange` が従っている規則そのものです。
`Arrange` はグループを「最初のウィンドウがある位置」の順に並べます。したがって、グループの
タブをまとめて塊で動かした結果は、`Arrange` がそのまま返す並びと一致します。何度計算しても
変わらないため、移動が保たれます。テストの `ArrangingAfterAGroupMoveChangesNothing` が
これを守ります。ここが崩れると、動かしたグループが元の位置へ跳ね返ります。

ウィンドウが1つだけのアプリと、実行ファイルを読めなかったウィンドウは、要素1個の塊として
扱われるので、単体で移動します。

**一度グループを動かしたドラッグは、そのグループだけを動かします。** グループを動かすと、
ポインターは運び終えたグループの上に残ります。これを「グループ内の移動」と読むと、掴んでいる
タブがポインターの位置のスロットへ引き寄せられ、利用者が触っていないタブの並びまで変わって
しまいます。実機では、グループを動かすとその中身の順番が入れ替わる形で現れました。`PlanDrag`
には、そのドラッグがすでにグループを運んでいるかどうかを渡し、運んでいる間はグループ内の移動を
返しません。グループの中の並べ替えは、グループから出ないドラッグで行います。

**グループを越える移動は、直前に行がずれた量と同じだけポインターが進むまで待ちます。**
判定は `TabStrip.MovedFarEnough` です。これは省いてよい処理ではなく、二度直しています。

`DropIndex` はポインターの位置だけを見るため、「このグループが相手の前にある」状態と
「後ろにある」状態を分けているのは、1ピクセルの境目だけです。手の揺れより厄介なのは、
グループを飛び越したタブが、飛び越した先から見ると「戻れ」と判定されることです。ポインターが
まったく動いていなくても、マウスが動くたびに往復します。実機では、単体のタブがグループの上で
左右にチラつく形で現れました。

測るのは**行がずれた量**であって、動いたタブの枚数ではありません。単体のタブが2枚のグループを
飛び越すときも、行は2枚のグループを動かしたときと同じ2スロット分ずれます。最初の対策は
「2枚以上動くとき」に限り、求める移動量もタブ1枚分の固定でした。どちらの意味でも足りて
いませんでした。今は、2枚分ずれたものを戻すにはタブ2枚分の移動が要ります。動かしたのと同じ
距離です。1スロット分のずれは隣との入れ替えで、掴んでいるタブ自身がポインターの下に入るため
半タブ分の余裕があり、助けは要りません。グループの中での移動も、もともと余裕があるため
止めません。

**レイアウトの計算には一切手を入れていません。** `TabStrip.Measure` はすべてのタブに同じ幅と
同じ間隔を与え、`DropIndex`、`ScrollToShow`、当たり判定はいずれも同じ刻みを前提にしています。
グループの境目だけ間隔を広げると、これらをまとめて書き換えることになり、「描かれている位置」と
「落ちる位置」が一致するという前提も崩れます。そこでグループは、タブ上端の色帯で示します。
同じグループのタブの間では色帯を隙間ごしにつなげ、グループ全体が1本の帯に見えるようにします。
グループの境目には、その同じ隙間の中に区切り線を引きます。もっと広い間隔が必要になったときは、
測り方をもう1つ用意し、刻みを読むすべての場所をそちらへ移す必要があります。それは別の変更です。

ウィンドウが1つだけのグループには色を付けません。色帯は「これらは同じまとまりです」と伝える
ものであり、1つしかないタブには伝えることがありません。同じアプリが2つ以上ない行のすべてに
色を付ければ、バー全体が色付きになるだけで、何も伝わりません。

### グループの色の決め方

`TabGrouping.AccentFor` は 0 から 7 までの番号を返します。この番号は `BarPalette.Accents` の
添字であり、使用中の配色での色を指します。ユーザーが色を選んだグループは、その色をそのまま
使います。それ以外は計算で決めます。計算は2段階です。

1段階目は、グループ名のハッシュです。名前を小文字にして FNV-1a を計算し、色数で割った余りを
使います。`string.GetHashCode` を使わず自分で書いているのは、.NET Core 以降ではプロセスごとに
値が変わるためです。それでは起動のたびに色が変わり、2つのターゲットフレームワークの間でも
違う色になります。

2段階目は、ハッシュだけでは色の重複を避けられないために必要です。色は8つしかなく、名前が
違っても余りが一致することは「まれ」ではありません。3グループで約3分の1、9グループ以上では
必ず重複します。同じ色のグループが2つあることは、色帯がいちばん避けたい状態です。そこで、
ユーザーが選んだ色を先に確保し、自動のグループを設定ファイルの並び順にたどります。名前から
決まる色が空いていればそれを使い、埋まっていれば次の空き色を使います。

並び順を基準にするのは、自然に変わることのない順序がこれしかないためです。これにより、
毎回同じ結果になります。代わりに、グループを追加すると、その後ろにあるグループの色が
変わることがあります。色を固定したい場合は、手動で色を選びます。

ここでの対象は、ユーザーが定義したグループだけです。アプリ1つで1グループになっているものは
設定ファイルに存在しないため、設定側で色を振り分けることができません。アプリが6つほど並べば、
色の重複は頻繁に起きます。

残りは `TabGrouping.AccentsFor` が、設定ではなく画面上の並びで処理します。重複が問題になるのは
隣り合ったときです。色帯は同じグループのタブの隙間をまたいでつながるため、同じ色のグループが
隣り合うと1つのグループに見えます。これは色帯がいちばん避けたい状態です。間に別のグループが
あれば、単に同じ色のグループが2つあるだけで、誤解は生じません。そこで行を先頭からたどり、
直前のグループと色が同じ場合は、どちらかを次の色へずらします。ずらすのは計算で決まった側です。
ユーザーが選んだ色はそのまま残し、隣のグループが譲ります。両方とも手動指定の場合は、どちらも
そのままにします。ウィンドウが1つだけのグループには色が付かず、そこで色帯が途切れるため、
その次のグループは直前と比べる必要がありません。

これは画面上の並びを基準にするため、タブをドラッグして隣が変わったときや、隣に新しい
ウィンドウが開いたときに、グループの色が変わることがあります。これがこの保証の代償です。
影響は、利用者が見ている隣り合う2グループにとどまります。すべてのグループを並び順で
振り分ける方式にすると、同じ不安定さがバー全体の色に及びます。

## ウィンドウの実行ファイルを調べる方法

`WindowService.GetExecutablePath` は `PROCESS_QUERY_LIMITED_INFORMATION` でプロセスを開き、
`QueryFullProcessImageNameW` で問い合わせます。`Process.MainModule.FileName` のほうが短く
書けますが、こちらは `PROCESS_VM_READ` を必要とします。この権限は、管理者権限のプロセスや
ビット数の異なるプロセスに対して拒否され、しかも結果ではなく例外が返ります。限定的な権限は
どちらの場合も許可されるため、完全には操作できない管理者権限のウィンドウでも、正しいグループに
入ります。

電卓・設定・フォトなどのパッケージアプリは、`ApplicationFrameHost.exe` が持つ
`ApplicationFrameWindow` の中に描かれます。そのまま問い合わせるとすべて同じ実行ファイルを
返し、1つのグループにまとまってしまうため、枠の子ウィンドウを調べます。

`ProcessInfoCache` が結果を記憶します。失敗した結果も記憶します。`RefreshTabs` は毎秒4回動く
ので、問い合わせを許可されないウィンドウに毎回聞き直すことになるからです。有効期限はありません。
ウィンドウの持ち主のプロセスは途中で変わらないためです。エントリは、アイコンのキャッシュと同じ
「今あるウィンドウの一覧」を使って捨てます。そのため、Windows が同じハンドルを再利用しても、
古い内容が返ることはありません。

グループ分けの判定にはフルパスではなくファイル名を使います。人がアプリを見分けるのはファイル名
だからです。同じプログラムを別のフォルダーに2つ入れても、見ている人にとっては1つのアプリです。
その代わり、どちらも `app.exe` という名前の無関係な2つのプログラムは、1つとして扱われます。

## 新しい版が出たことを知らせる仕組み

リリースに添付するのは実行ファイル1つで、利用者はそれを自分のフォルダーへ置いて使います。
インストーラーもパッケージ管理の仕組みもないため、新しい版が出たことを伝える手段がほかに
ありません。そこでバーは、GitHubにある最新のリリースの版番号を読み、新しければお知らせします。
**行うのはそこまでです。** ダウンロードも置き換えも行いません。

これは途中段階ではなく、意図した範囲です。実行ファイルに署名がないため、取得した置き換え用の
ファイルを照合する手段が乏しいこと。置き換えに失敗すると、起動できない実行ファイルだけが
利用者の手元に残ること。#21 のインストーラーが `Program Files` に置くようになれば、
書き換えに管理者権限が必要になり、設計をやり直すことになること。知らせるだけなら、そのどれも
起きません。

**版番号は `api.github.com/repos/.../releases/latest` から読みます。** 解析には
`DataContractJsonSerializer` と、使う1項目だけを書いた契約を用います。設定ファイルと同じ道具で
あり、JSON用のNuGetパッケージは追加しません。単一の実行ファイルとして配布するためです。
名前を書いているのは `tag_name` だけなので、応答のほかの部分が変わっても読み取りは壊れません。
もう一つの案は `github.com/.../releases/latest` のリダイレクト先を読む方法で、解析処理が
まったく不要でした。取り決めが公開されている側を選び、未認証で1時間あたり60回という上限を
受け入れています。1日1回の確認では届かない数です。

**シェルに渡すアドレスは定数です。** `UpdateService.LatestReleaseUrl` は同じファイルにある
所有者名とリポジトリ名から組み立てており、応答に含まれていた値は使いません。`Process.Start` は
渡されたものを開くため、応答から取ったURLは「応答した相手が選んだURL」になってしまいます。

**確認はバーが表示されてから10秒後に行います。** ログオン時は、最初のウィンドウが描かれる時点で
通信の準備が整っていないことがよくあります。すぐ確認すると、リリースの有無とは関係のない理由で
失敗します。既にある250ミリ秒のタイマーに相乗りしており、タイマーは増やしていません。

**利用者が求めていない限り、何も表示しません。** 自動の確認は、失敗したときも新しい版がないときも
無言です。理由は `SettingsStore.Load` が対話箱を出さない理由と同じで、バーはログオン時に起動し、
そこには誰も見ていないからです。メニューの `Check for updates...` は必ず答えます。人が押した
操作だからです。処理は1つで、どちらかを示す引数で切り替えます。

**同じ版のお知らせは1回だけです。** 設定の `LastNoticedRelease` に最後に伝えた版を持ちます。
比較は文字列ではなく版番号として行うため、`v0.4.0` と `0.4.0` が別の知らせになることは
ありません。これがないと、利用者が更新するまで毎回のログオンでお知らせが出て、注意喚起が
邪魔者に変わります。

**最後に確認した時刻は、GitHubが答えたときだけ記録します。** ログオン時に通信できなかった機械は、
次の起動でもう一度試すべきで、さらに1日待つべきではありません。

**`AppSettings.CheckForUpdates` は `bool` ではなく `bool?` です。**
`DataContractJsonSerializer` は構築子を実行しないため、この設定ができる前に書かれた設定ファイル
を読むと、この項目は未設定のまま残ります。`bool` だと `false` として届き、すでにアプリを使って
いる人だけが機能を切られ、新規に導入した人には有効なまま、という状態になります。null は
「未選択」を表し、`Normalized` が有効として読みます。手で書いた `false` はそのまま尊重します。

**メニューの項目は、開くときに自分で文言を決めます。** `BuildMenu` はバー用とトレイ用で2回
呼ばれるため、どの項目にも実体が2つあり、フィールドでは片方しか指せません。`Opening` の処理も
`BuildMenu` の中で登録しているので、2つの複製が1か所から同じ動きを受け取ります。

**メニューは再起動をまたいで覚えます。通知は覚えません。** 起動時に `LastNoticedRelease` を
読み、その版がこのビルドより新しければ、確認を実行する前からメニューにそう表示します。確認は
1日1回までなので、同じ日に起動し直すと確認は走りません。この仕組みがないと、新しい版が設定
ファイルに記録されているのに、メニューは「Check for updates...」に戻ってしまいます。通知そのものは
これまでどおり1つの版につき1回だけです。確認の結果が「最新」だった場合は記録を消すので、
古い表示が残ることはありません。

**時刻は文字列で保存します。** `DataContractJsonSerializer` は `DateTime` を
`/Date(1757246400000+0900)/` の形で書き出します。時間帯が付き、人が読むことも打ち込むことも
できません。設定ファイルは手で編集できることを前提にしています。

通信にも画面にも依存せずに決められることは、すべて `Core/Update/` にあります。タグから版番号を
読むこと、2つを比べること、確認の時期が来たかを判断することの3つです。
`Services/UpdateService.cs` は要求を出し、3種類の結果のどれかを返します。答えを受け取る
スレッドと、利用者に見えるものは、すべて `MainForm` が持ちます。

## 資源の持ち主と、漏れの見つけ方

このバーはログインしている間ずっと動きます。解放し忘れた資源は、その回のセッションが終わるまで
戻ってきません。そのため、どのオブジェクトを誰が持つのかを決めてあります。

| オブジェクト | 持ち主 | 解放する場所 |
|---|---|---|
| ウィンドウのアイコン | `MainForm` の `_iconCache` | ウィンドウを閉じたとき、アイコンを取り直したとき、`ReleaseResources` |
| フォント、ツールチップ、2つのメニュー、通知領域アイコン、タイマー | `MainForm` | `ReleaseResources` |
| `ExtractIconExW` で得たアイコンハンドル | `MainForm` | `ReleaseResources` の `DestroyIcon` |
| `SetWinEventHook` のフック | `MainForm` の `_hooks` | `ReleaseResources` の `UnhookWinEvent` |
| AppBar の登録 | `MainForm` | `ReleaseResources` の `UnregisterAppBar` |
| `OpenProcess` で得たプロセスハンドル | `WindowService.GetExecutablePath` | 同じメソッドの `finally` の `CloseHandle` |
| 描画中の `Pen`、`SolidBrush`、`GraphicsPath` | 囲っている `using` | `using` を抜けるとき |
| 更新確認の `HttpClient` と応答 | `UpdateService.FetchLatestTag` の `using` | `using` を抜けるとき |
| リリースページを開いたときに `Process.Start` が返すプロセス | `MainForm.OpenReleasePage` の `using` | `using` を抜けるとき |
| `SettingsForm` の各コントロール | 追加先の `Controls` | フォーム自身の `Dispose` |

`ReleaseResources` は2か所から呼ばれ、実際の処理は最初の1回だけ行います。1つは
`OnFormClosing` で、バーを閉じた時点で画面の領域を返すためです。もう1つは `Dispose(bool)` で、
閉じずに破棄された場合でも登録を残さないためです。基底クラスの `Dispose` より先に動かします。
AppBar の登録解除には、まだ有効なウィンドウハンドルが必要だからです。

これを守るために、3つの解析ルールを `.editorconfig` で警告に設定しています。ビルドは警告を
エラーとして扱うため、違反があればビルドが失敗します。

- `CA1001`：破棄が必要なフィールドを持つのに、自身が破棄可能でない型
- `CA2000`：作ったまま破棄されないオブジェクト
- `CA2213`：`Dispose` が解放していないフィールド

`Directory.Build.props` の `EnableNETAnalyzers` は、これらを `net48` 側にも適用するための設定
です。この指定がないと、SDK は `net48` を解析しません。

Windows Forms のコンテナが持ち主になっているフィールド、たとえば `Controls` に追加した
コントロールやメニューに追加した項目には、持ち主を書いた `SuppressMessage` を付けています。
`CA2213` はこの種の所有関係を判別できず、二重の解放を求めてくるためです。`CA2000` に
`dispose_ownership_transfer_at_method_call` を設定しているのも同じ理由です。この設定がないと、
コレクションに追加したコントロールがすべて「破棄し忘れ」と報告されます。

解析はソースコードを読むだけなので、動かしている間に増え続ける状態までは分かりません。そこは人
が確認します。

1. バーを起動し、タスクマネージャーの「詳細」タブを開きます。
2. 「メモリ」「ハンドル」「USER オブジェクト」「GDI オブジェクト」の列を表示し、
   `WindowsSimpleTaskTabBar.exe` を探します。
3. ウィンドウの開閉、バーの高さの変更、タブの並べ替え、メニューの開閉を、30分以上続けます。
4. 4つの数値が上下しながら落ち着けば問題ありません。上がり続ける数値があれば、それが報告すべき
   兆候です。
